# DummyPay – STP (System Test Plan)

## 1. מבוא ומטרה

מסמך זה מגדיר איך נבדקת מערכת DummyPay לפני שחרור: מה נבדק, באילו שיטות, מתי הבדיקות מתחילות ומתי הן נחשבות גמורות.

האתר DummyPay הוא מערכת תשלומים מדומה ([dummypay.vercel.app](https://dummypay.vercel.app/)). משתמשים רשומים יכולים לשלוח ולקבל כסף, להוסיף כרטיסי אשראי וחשבונות בנק, ולנהל את החשבון שלהם. לא עובר בה כסף אמיתי.

**קהל היעד:** מנהל/ת המוצר. המסמך מאפשר לאשר את היקף הבדיקות ואת הקריטריונים לשחרור.

**מסמכים קשורים:** STD (תיאור בדיקות מערכת) שמפרט את כל מקרי הבדיקה, ו-repository האוטומציה ב-GitHub.

## 2. תחום הבדיקות

נבדקת הפונקציונליות של אתר ה-Web דרך ממשק המשתמש, בעבודה ידנית ובאוטומציה.

**בתחום (In scope):**

- התחברות, שחזור סיסמה והתנתקות
- כל עמודי המערכת שזמינים למשתמש מחובר (פירוט בסעיף 3)
- ולידציה של שדות והודעות שגיאה
- בדיקות חיוביות ושליליות לכל עמוד
- בדיקות API ישירות מול שירותי DummyPay ב־Supabase,. הבדיקות יכסו פעולות תקינות, קלט שגוי וגישה לפעולות המחייבות התחברות.
- דפדפן Chromium במחשב שולחני

**מחוץ לתחום (Out of scope):**

- בדיקות עומס וביצועים (Load / Performance)
- בדיקות אבטחה וחדירות (Penetration)
- אפליקציית מובייל ותצוגה בטלפון
- דפדפנים נוספים (Firefox, Safari)
- נגישות (Accessibility)
- עמוד ההרשמה (Register). משתמשי הבדיקה נוצרים מראש ומשמשים את כל הבדיקות

## 3. פיצ'רים לבדיקה

1. עמוד **Login**: כניסה עם פרטים תקינים, סיסמה שגויה, שדות ריקים ופורמט מייל. עדיפות: High.
2. עמוד **Forgot Password**: שליחת בקשה למייל קיים ולמייל שלא קיים. עדיפות: Medium.
3. עמוד **Dashboard**: סקירה כללית אחרי התחברות וניווט לשאר העמודים. עדיפות: High.
4. עמוד **Wallets**: יתרה כוללת ויתרה לכל ארנק מטבע, הוספת ארנק (Add wallet), תצוגת המרה (Conversion preview) ושערי חליפין. עדיפות: High.
5. עמוד **Send Money**: שליחה למשתמש רשום, סכום 0 או שלילי, סכום מעל היתרה ונמען שלא קיים. עדיפות: High.
6. עמוד **Transaction History**: הופעת עסקה חדשה (שליחה וקבלה), פרטים נכונים, סינון וחיפוש. עדיפות: Medium.
7. עמוד **Payment Cards**: הוספת כרטיס תקין, מספר שגוי, תוקף שעבר, CVV שגוי ומחיקת כרטיס. עדיפות: High.
8. עמוד **Bank Accounts**: הוספת חשבון, שדות חסרים או לא תקינים ומחיקת חשבון. עדיפות: Medium.
9. עמוד **Notifications**: הופעת התראות על פעולות בחשבון, למשל קבלת כסף. עדיפות: Low.
10. עמוד **Profile & Settings**: עדכון פרטים, שינוי סיסמה והתנתקות. עדיפות: Low.

## 4. אסטרטגיית בדיקות

הבדיקות מתחילות בחקירה ידנית של המוצר, מתועדות ב-STD וממומשות באוטומציה. כל בדיקה ב-STD הופכת לטסט אוטומטי אחד לפחות.

**סוגי בדיקות:**

1. בדיקות **Smoke**: מעט בדיקות קריטיות שמוודאות שהמערכת עובדת: התחברות, שליחת כסף והוספת כרטיס. רצות בכל Pull Request, בפחות מ-5 דקות.
2. בדיקות **Regression (Nightly)**: כל הבדיקות, כולל מקרי קצה ובדיקות שליליות. רצות פעם בלילה ולפני שחרור.
3. **חיוביות:** נתונים תקינים, והפעולה מצליחה. 3-5 לכל עמוד, בתוך Smoke או Regression.
4. **שליליות:** נתונים שגויים, ומצפים להודעת שגיאה מתאימה. 3-5 לכל עמוד, בתוך Regression.
5. **ידניות (Exploratory):** חקירת המוצר ואיתור באגים לפני כתיבת ה-STD. בתחילת הפרויקט ובכל פיצ'ר חדש.
6. בדיקות API יבדקו את קוד התגובה, תוכן התגובה והשינוי בנתוני המערכת בהתאם לפעולה. הן יתועדו ב־STD ויסומנו כ־Smoke או Regression לפי חשיבותן. פעולות שיוצרות נתוני בדיקה יכללו ניקוי כשאפשר, כדי לאפשר הרצות חוזרות.

**עדיפויות:**

- עדיפות **High**: תקלה חוסמת שימוש במוצר או פוגעת בכסף (התחברות, שליחת כסף, יתרה)
- עדיפות **Medium**: תקלה בפיצ'ר חשוב שיש לו עקיפה
- עדיפות **Low**: תקלה קוסמטית או שולית

**גישת האוטומציה:** תבנית Page Object Model. לכל עמוד יש מחלקה עם האלמנטים והפעולות שלו, והטסטים משתמשים בה. כל טסט מסומן כ-smoke או כ-regression, כך שאפשר להריץ כל קבוצה בנפרד.

## 5. סביבה, כלים ונתונים

הבדיקות רצות על סביבת האתר הציבורית, מהמחשב המקומי ומ-GitHub Actions.

1. **כתובת המערכת:** [dummypay.vercel.app](https://dummypay.vercel.app/)
2. **שפה ו-framework:** Python, Playwright, pytest
3. **דפדפן:** Chromium (Playwright)
4. **ניהול קוד:** Git + GitHub, עבודה בברנצ'ים ו-Pull Request עם Code Review חובה
5. **הרצה אוטומטית (CI):** GitHub Actions. Smoke רץ בכל Pull Request, ו-Regression רץ בלילה
6. **דוחות:** דוח HTML לכל הרצה, שנשמר כ-artifact ב-CI
7. **תיעוד:** STP, STD ודוח באגים
8. בדיקות ה־API ירוצו באמצעות Pytest ו־Playwright APIRequestContext. ההתחברות תתבצע עם משתמשי הבדיקה A ו־B, ותשתמש ב־access token לבקשות המחייבות הזדהות. כתובת ה־API ומפתח הפרויקט ייטענו ממשתני סביבה.

**נתוני בדיקה:**

- 2 משתמשי בדיקה יעודיים קבועים.
- כרטיס הבדיקה שסופק לפרויקט (מספר הבדיקה הסטנדרטי 4111…)
- נתונים שגויים מכוונים לבדיקות שליליות: מייל לא תקין, סכום שלילי, כרטיס שתוקפו פג
- כל הנתונים שמורים בקובץ נתונים אחד בפרויקט האוטומציה, לא בתוך הטסטים

## 6. קריטריוני כניסה ויציאה

**Entry criteria:**

- האתר זמין ועולה בכתובת הסביבה
- ה-STD מאושר, עם לפחות 30 בדיקות
- סביבת האוטומציה מוקמת ומשתמשי הבדיקה מוכנים
- כל בדיקות ה-Smoke עוברות. אם Smoke נכשל, לא ממשיכים ל-Regression

**Exit criteria:**

- 100% מבדיקות ה-STD הורצו
- 100% מבדיקות ה-Smoke עוברות
- לפחות 90% מבדיקות ה-Regression עוברות
- אין באגים פתוחים בחומרת Critical או High
- דוח הרצה ודוח באגים הועברו למנהל/ת המוצר

## 7. ניהול באגים

כל באג נפתח ב-GitHub Issues עם כותרת, צעדים לשחזור, תוצאה צפויה, תוצאה בפועל, צילום מסך וחומרה.

**רמות חומרה:**

1. חומרה **Critical**: המערכת או פעולת כסף לא עובדת, ואין עקיפה. לדוגמה: אי אפשר להתחבר, או שכסף יורד בלי שהגיע למקבל.
2. חומרה **High**: פיצ'ר מרכזי שבור או נותן תוצאה שגויה. לדוגמה: אפשר לשלוח סכום שלילי.
3. חומרה **Medium**: תקלה עם עקיפה או בפיצ'ר משני. לדוגמה: הודעת שגיאה לא מופיעה, אבל הפעולה נחסמת.
4. חומרה **Low**: קוסמטי או ניסוח. לדוגמה: שגיאת כתיב, או כפתור לא מיושר.

**מחזור חיים של באג:** New → Open → Fixed → Retest → Closed (או Reopened אם התיקון לא עבד).

## 8. סיכונים והנחות

**סיכונים ומה עושים:**

1. **האתר משתנה בזמן הפרויקט:** לוקייטורים נשברים וטסטים נכשלים. משתמשים בלוקייטורים יציבים, וכולם נמצאים במקום אחד ב-Page Objects.
2. **האתר לא זמין או איטי:** טסטים נכשלים שלא בגלל באג. משתמשים בהמתנות חכמות במקום המתנות קבועות, ומריצים שוב לפני שפותחים באג.
3. **נתונים מתנגשים בין טסטים:** טסט אחד משפיע על התוצאה של טסט אחר. צמצום תלויות בין טסטים עד ל-0.
4. **קונפליקטים בקוד בין חברות הצוות:** עיכוב במיזוג. עובדים בברנץ' נפרד לכל חבר צוות, עם Pull Request קטנים.
5. **מגבלת זמן:** לא כל העמודים מכוסים. נותנים עדיפות לבדיקות High ו-Smoke.

**הנחות:**

- המערכת היא סימולציה ולא מעבירה כסף אמיתי, ולכן מותר לבצע עליה פעולות כספיות בבדיקות
- אין מסמך דרישות רשמי. התוצאה הצפויה נקבעת לפי התנהגות סבירה של מערכת תשלומים

## 9. שלבים ותוצרים

העבודה מתוכננת בשבעה שלבים, כשכל שלב מסתיים בתוצר. תאריכי יעד ייקבעו לפי מועד ההגשה.

1. **הקמה:** repository, הרשאות, הגנה על main ומבנה פרויקט
2. **חקירת המוצר:** רשימת עמודים מלאה ובאגים ראשונים
3. **תיעוד:** STP זה ו-STD עם 30 בדיקות לפחות
4. **תשתית אוטומציה:** הגדרות, fixtures ו-base page
5. **כתיבת Page Objects וטסטים:** 3-5 חיוביים ו-3-5 שליליים לכל עמוד
6. **הרצה אוטומטית ודוחות:** GitHub Actions ודוח HTML
7. **סגירה:** הרצה מלאה, דוח סיכום והגשה

**תוצרים:**

1. מסמך **STP**: מסמך זה.
2. מסמך **STD**: כל מקרי הבדיקה, עם עדיפות וסיווג Smoke / Regression.
3. **קוד אוטומציה:** Repository ב-GitHub עם Page Objects וטסטים. בדיקות API ותשתית משותפת לשליחת בקשות ולהתחברות, לצד בדיקות ממשק המשתמש.
4. **דוח הרצה:** דוח HTML של תוצאות הבדיקות.
5. **דוח באגים:** כל הבאגים שנמצאו, עם חומרה וסטטוס.
